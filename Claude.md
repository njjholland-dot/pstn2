## Project Overview

PSTN2 is a telecom industry standards project that tackles critical problems in the global Public Switched Telephone Network (PSTN). The project focuses on:

- Caller ID verification and fraud prevention without a centralized numbering database (CDB)
- End-to-end encryption
- Direct routing
- A distributed messaging architecture in which each Communication Provider (CP) keeps its own data

**Key terminology:**
- **CP** (Communication Provider): telecom range holders and carriers
- **Range Holder**: the CP that Ofcom allocated a number block to, as named in Ofcom's S1–S9 numbering lists. It always knows where its ported-out numbers went.
- **CDB** (Central Database): a proposed centralized industry numbering database. This project explicitly avoids needing one.
  - Comparison figures used everywhere: **~£2m to build, ~£600k a year to run (30% a year)**.

## Architecture Principles

**Distributed over centralized:**
Everything a central database would hold already exists:
- Ofcom knows who each block is allocated to.
- Range Holders know where their ported numbers went.
- Every CP knows the numbers it serves.

PSTN2 asks the right party instead of copying the data into a central store.

**Edge implementation:**
Everything can be implemented "at the edge" and "over the top", with no changes to the existing PSTN infrastructure. CPs can adopt at their own pace with minimal investment.

**Short-lived data objects:**
Call setup data objects only need to exist for about 30 seconds, which allows low-cost, high-performance, memory-based solutions.

**Optional participation:**
Unlike STIR/SHAKEN, participation is optional. A block with no Range Holder URL simply uses today's network.

## Key Technical Processes

### Number Discovery (who has this number?)
1. Check the local cache. Every PSTN2 response can carry `cache.invalidate`.
2. On a miss, look the number up in the local copy of Ofcom's S1–S9 list (longest prefix) to get the Range Holder and its URL.
3. Ask the Range Holder. It answers `held`, or `redirect` to the CP the number was ported to.
4. Retry at that CP.
5. Cache the answer per number, and go direct next time.

### Fraud Control 1: Caller ID Verification
1. The caller ID owner creates a data object when placing a call.
2. The recipient CP discovers the caller ID's holder (Number Discovery) and queries it.
3. The recipient verifies the call from the returned data. A `not_held` answer means: rediscover and retry.
4. Optionally, the data object includes caller name and call purpose for routing decisions.

### Fraud Control 2: End-to-End Encryption
1. The call setup data object includes the caller's public key.
2. The recipient CP can add its own public key.
3. Media is encrypted with SRTP. Keys come from DTLS-SRTP, and the Ed25519 identity keys authenticate the fingerprints.

### Direct Routing
1. The caller CP discovers the destination's holder and asks it for permission to call.
2. The recipient returns an IP/port for a direct SIP invite.
3. This removes the traditional PSTN routing overhead.

## Technical Stack

### Presentations and website
- HTML5/CSS3, vanilla JavaScript ES modules, and D3.js v7 (self-hosted).
- Pre-rendered narration: macOS `say` with an en-GB voice, then ffmpeg loudnorm to MP3.
  - The live Web Speech fallback uses the Law Enforcement voice ranking (Google en-GB, Neural en-GB, Daniel, Kate).
- Inter font and Lucide icons (ISC licence), both self-hosted. **No emoji in presentations.**

### SDKs
- **TypeScript 5:** zero runtime dependencies (global fetch, node:crypto).
- **Python 3.11+:** httpx, pydantic v2, cryptography.
- **Go 1.21+:** standard library only.
- **User-Agent:** every client sends `pstn2-<lang>-sdk/1.1.0`. The pstn2.org WAF returns 403 to `curl/*` and `Go-http-client/*`.

### Infrastructure
- **Hosting:** NetworkSolutions, static files only (pstn2.org).
- **Deployment:** `./deploy.sh` (lftp mirror over SFTP).
- **Version control:** GitHub, https://github.com/njjholland-dot/pstn2 (public).

### Standards and protocols
- OpenAPI 3.0.3, Ed25519 (RFC 8032), TLS 1.3, SRTP/DTLS-SRTP, JSON, E.164.

## Deployment Process

```bash
export PSTN2_FTP_PASSWORD='<SFTP password>'   # from the local credentials vault
./deploy.sh --stage-only # build the site into .deploy-stage/ (no credentials needed)
./deploy.sh --dry-run    # preview what would be uploaded
./deploy.sh              # deploy changed files
./deploy.sh --full       # re-upload everything
```

- The script stages the repo into the site layout, uploads only newer files, and never deletes remote files; other projects share the host under /htdocs.
- Commit before deploying: the zips are built from HEAD.
- After deploying, run `test-environment/conformance/run.sh --live`.

Credentials are never stored in the repo. The test-CP signing keys live in `tools/testcp/.keys.json` (gitignored) and in the vault.

## Key Design Patterns

### Presentation structure (shared player)
- **`narration.json`:** scenes → segments of 1–2 sentences. Captions show the text; the voice reads it, with `lexicon.js` handling pronunciation.
- **`scenes.js`:**
  - `createDeck({ scenes: { id: { build(s), cues: { segId: fn } } } })`
  - cues fire when their segment starts playing;
  - use `s.wait` / `s.t` for timing, never raw timers.
- **Audio:** `node tools/narrate/build-narration.mjs <deck>` is idempotent and keyed by text hash.
- **Consistent cast:** Alpha Telecom 020 7946 0xxx (blue), Bravo Networks 0161 496 0xxx (green), Charlie Comms 0113 496 0xxx (amber). All are Ofcom drama-range numbers.

### Code example structure
Every language has the same six examples:
1. basic authentication
2. direct routing
3. token pool
4. emergency services
5. complete call flow
6. number discovery

They default to the local mock network (`PSTN2_NETWORK=local`). Example 06 also runs live (`PSTN2_NETWORK=live`).

### Documentation structure
- **README.md:** quick start, installation, API reference
- **SPECIFICATION.md:** complete protocol details
- **EXAMPLES.md:** detailed usage guide

Each document includes code snippets in all three languages.

## Performance Targets

- **Authentication:** < 100ms (95th percentile)
- **Call setup:** < 1 second total
- **Number Discovery:** < 1ms on a cache hit; < 50ms per hop
- **Token Pool:** < 50ms for verification
- **Fallback:** traditional PSTN is always available
